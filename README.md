# VLESS Shop Bot — RIXXX Edition

Telegram-магазин подписок для [Panel-Naive-Mieru-by-RIXXX](https://github.com/cwash797-cmd/Panel-Naive-Mieru-by-RIXXX).

- Форк: https://github.com/cwash797-cmd/vless-shopbot-rixxx-edition
- Исходная RIXXX Edition: https://github.com/detkeroot/vless-shopbot-rixxx-edition
- Лицензия: [GNU GPL v3.0](LICENSE).

## Статус и границы совместимости

Эта ветка исправляет проблемы безопасности и надёжности исходного бота. Она **не является подтверждением готовности конкретной рабочей инфраструктуры**: перед продажами выполните приёмку ниже.

| Возможность | Состояние |
|---|---|
| Создание/продление Naive, Mieru, Hy2 | Адаптер REST API RIXXX v1.11+ |
| Федерация | Deploy после создания/продления; проверка результатов отдельных нод |
| Единая подписка | Бот передаёт `/sub/:token`, полученную от панели; формат формирует сама панель |
| Бонусные URI, включая VLESS | Персональный список панели через `/bonus`; без смены активного токена подписки |
| Самостоятельный CRUD в 3x-ui | **Не реализован**. VLESS из 3x-ui можно добавить только как готовый бонусный URI |
| Lava.top | СБП/карты, обязательный ключ вебхука, ручной опрос статуса |
| ЮKassa | Проверка платежа через API провайдера, сверка суммы и валюты |
| Crypto Pay | Проверка HMAC исходного тела запроса, сверка локального счёта, суммы и валюты |
| Heleket | Подпись по протоколу провайдера и сверка локального заказа |
| TON Connect | **Отключён**: прежняя реализация не проверяла блокчейн и сумму |
| 2FA веб-панели | Необязательный TOTP через `ADMIN_TOTP_SECRET`; код требуется при входе |

Бонусные ссылки **не означают автоматическое создание или продление чужих ключей**. Их работоспособность, срок действия и отзыв управляются на исходном сервере. Удаление подписки RIXXX не отзывает уже импортированные независимые бонусные credentials.

## Безопасный запуск

Требуются Linux, Docker с Compose v2 и Python 3 для генерации конфигурации. Не запускайте установщик панели и бота одновременно. Одна копия бота на одну SQLite-базу и один Telegram-токен.

До слияния PR используйте ветку `genspark_ai_developer`; `main` форка пока содержит исходный код:

```bash
git clone https://github.com/cwash797-cmd/vless-shopbot-rixxx-edition.git
cd vless-shopbot-rixxx-edition
git switch genspark_ai_developer
bash install.sh --check
```

Команда создаёт `.env` с отдельными случайными `ADMIN_PASSWORD` и `FLASK_SECRET_KEY` и правами `0600`. Секреты не печатаются в логи. `--check` не запускает контейнеры.

1. Прочитайте `.env` локально. Никому не пересылайте этот файл.
2. Настройте HTTPS reverse proxy на `127.0.0.1:1488` — [руководство](RIXXX_INTEGRATION.md).
3. Запустите `docker compose up -d --build`.
4. Откройте `https://bot.example.com/login`. Логин: `admin`, пароль: значение `ADMIN_PASSWORD` из `.env`.
5. Заполните токен Telegram, username без `@`, положительный числовой ID владельца.
6. Добавьте **один Hub RIXXX**, затем тарифы этого Hub. Название хоста — до 26 UTF-8 байт; для простоты используйте `Hub`.
7. Сохраните настройки и запустите бота. Пользователям и саппорту нужно сначала написать ему `/start`.

Установщик больше **не устанавливает пакеты, не меняет firewall, не удаляет Nginx-конфиги и не дописывает JavaScript в Caddy-шаблон панели**. Не используйте прежнюю команду `curl | sudo bash` из старых отчётов.

Внешний порт `1488` закрыт привязкой Docker к loopback. В `.env` оставьте `COOKIE_SECURE=true` при HTTPS. Для временной работы исключительно через локальный SSH-туннель можно установить `COOKIE_SECURE=false` и пересоздать контейнер. Не используйте этот режим на открытом HTTP-сайте.

### 2FA

Сгенерируйте TOTP-секрет доверенным локальным инструментом, добавьте его в приложение-аутентификатор и в `ADMIN_TOTP_SECRET` внутри `.env`, затем выполните `docker compose up -d --force-recreate`. Код приложения нужно вводить вместе с паролем. Секрет 2FA не отправляйте в чат. Веб-мастера подключения и recovery-кодов пока нет; резервную копию секрета храните отдельно.

### Обновление существующей установки

- Сначала остановите контейнер: `docker compose stop`.
- Сохраните резервные копии `users.db` и `.env` в защищённое место. В базе есть токены провайдеров, Telegram и данные доступа к панели.
- Проверьте diff/PR и переключитесь на нужную ветку.
- Для новой `.env` выполните `bash install.sh --check`; существующая `.env` не перезаписывается. Если файл уже существует, добавьте недостающие переменные вручную.
- Старый пароль `admin` заменяется значением `ADMIN_PASSWORD` длиной не менее 12 символов. При отсутствии такого значения запуск останавливается. Другие старые пароли мигрируют в хеш; смените слабые пароли вручную.
- Старый известный секрет Flask и пример `generate_random_secret_key_here` отвергаются. Сгенерируйте отдельную случайную строку не короче 32 символов.
- Запустите `docker compose up -d --build` и пройдите приёмку.

Финансовая история сохраняется. Ранее зависшие платежи не переисполняются автоматически: старые `paid` могли означать лишь получение вебхука, а не фактическую выдачу ключа. Сверьте их отдельно.

## Размещение и бесплатные варианты

Для этого Python/Docker-проекта наиболее простой вариант без нового счёта за хостинг — существующий VPS с RIXXX, отдельный контейнер и достаточный запас ресурсов. Недостаток: сбой VPS одновременно затронет VPN и магазин; храните резервные копии вне этого VPS. Для лучшей изоляции и независимой доступности можно выделить другой сервер, но это уже отдельные расходы.

Cloudflare DNS/proxy не является хостингом процесса бота. Текущие Flask/Waitress, Telegram polling, файловая SQLite и фоновый планировщик не переносятся в Workers без адаптации. Бесплатная архитектура может использовать Telegram webhooks → Worker → D1, отдельный webhook Lava и задания восстановления через Cron/Queues. VPN-ноды и RIXXX всё равно остаются на VPS; Workers не заменяет VPN-серверы.

На момент проверки официальные лимиты Workers Free — 100 000 запросов/день и 10 мс CPU на вызов; D1 Free — 5 млн прочитанных и 100 000 записанных строк/день, 5 ГБ хранения суммарно. Это общие квоты аккаунта, не обещание бесплатной работы при любой нагрузке. Контейнеры Cloudflare требуют Workers Paid (от $5/месяц плюс возможное потребление), так что перенос Docker ради бесплатности не подходит.

Источники: [Workers](https://developers.cloudflare.com/workers/platform/pricing/), [D1](https://developers.cloudflare.com/d1/platform/pricing/), [Containers](https://developers.cloudflare.com/containers/pricing/), [Python Workers](https://developers.cloudflare.com/workers/languages/python/how-python-workers-work/).

## Команды владельца и саппорта

Команды магазина работают только в личном чате, не в группах.

| Команда | Доступ и действие |
|---|---|
| `/give <Telegram ID> <дней>` | Владелец/саппорт: новый ключ на первом настроенном хосте, 1–36500 дней |
| `/grant <Telegram ID>` | Только владелец: разрешить `/give` зарегистрированному пользователю |
| `/revoke <Telegram ID>` | Только владелец: отозвать разрешение на `/give`, не VPN-ключи |
| `/keys <Telegram ID>` | Только владелец: внутренние ID ключей для управления бонусами |
| `/bonus <ID ключа> <URI…>` | Только владелец: **заменить весь** список бонусных URI; до 30 ссылок через пробел |
| `/bonus <ID ключа> clear` | Очистить персональные бонусные URI |
| `/ban <Telegram ID>` | Заблокировать бота и попытаться отозвать все ключи Hub/федерации |
| `/unban <Telegram ID>` | Открыть доступ к боту; ранее отозванные VPN-ключи не восстанавливаются |
| `/delete_user <Telegram ID>` | Удалить профиль и сбросить триал только после подтверждённого отзыва всех ключей |
| `/setref <Telegram ID> <процент>` | Персональная реферальная ставка, от 0 до 100 |
| `/delref <Telegram ID>` | Вернуть общую ставку |
| `/users` | Отчёт по пользователям |
| `/approve_withdraw <Telegram ID>` | Учёт ручной выплаты реферального баланса; перевод денег выполняет оператор |
| `/decline_withdraw <Telegram ID>` | Отказать в заявке на вывод |

Права `/give` не дают доступа к `/grant`, `/bonus` или веб-админке. Ответы через отдельного support-бота разрешены администраторам настроенной support-группы. Не добавляйте покупателей в эту группу.

При частичном отзыве профиль/неотозванные ключи остаются в базе. Восстановите связь с нодами и повторите операцию. До подтверждения **нельзя считать VPN-доступ полностью отозванным**. Бонусные ключи внешних серверов отзывайте отдельно.

Пробный период резервируется атомарно перед обращением к панели. При неоднозначном сетевом сбое он не запускается повторно: оператор должен проверить панель и помочь пользователю, а не выдавать дополнительные бесплатные периоды автоматически.

## Платёжные шлюзы

Настройки задаются в веб-панели. После изменения реквизитов перезапустите магазин кнопками остановки/запуска.

### Lava.top

Интеграция дополнительно сверена с официальной [OpenAPI 1.22.0](https://gate.lava.top/docs/documentation.yaml) ([Swagger](https://gate.lava.top/docs)). Это спецификация `lava.top`, не другого сервиса `lava.ru`.

Нужны API Key, Offer ID (или Product ID для автоматического определения оффера) и **отдельный Webhook Key**. Продукт должен поддерживать динамическую цену; текущий код рассчитан на одноразовые счета.

- Вебхук: `https://bot.example.com/lava-webhook`.
- Событие: `payment.success`.
- Аутентификация: заголовок `X-Api-Key`, совпадающий с Webhook Key в боте.
- СБП: `PAY2ME` / `SBP`, валюта `RUB`.
- «Проверить оплату» доступно только владельцу локального счёта. `GET /api/v1/invoices/{id}` возвращает `COMPLETED`; бот проверяет также идентификатор, `receipt.amount` и `receipt.currency`. Комиссия `receipt.fee` не вычитается при сравнении цены заказа.
- Вебхук одноразовой покупки должен содержать `eventType=payment.success`, `status=completed`, совпадающие `contractId`, `amount`, `currency`.
- Ответ создания счёта проверяется по `amountTotal`; при отличии цены/валюты ссылка покупателю не выдаётся.
- Автопоиск оффера учитывает `items[].data.offers` и пагинацию. Если у товара несколько офферов, укажите конкретный Offer ID — первый попавшийся не выбирается.
- По документации Lava ответы 2xx **и 3xx** считаются доставкой, а 4xx/5xx вызывают до 19 повторных попыток. Указывайте конечный HTTPS URL `/lava-webhook` без редиректа, страницы входа, Cloudflare challenge или кеширования. Не заменяйте ответы 503 обработчика на 200 на reverse proxy.

Повторное событие того же contract ID не продлевает подписку ещё раз. Поддержка полноценного рекуррентного биллинга и возвратов не реализована.

### ЮKassa / Crypto Pay / Heleket

- ЮKassa: Shop ID + Secret Key, вебхук `/yookassa-webhook`. Перед выдачей бот запрашивает платёж у ЮKassa. Данные тарифа берутся из своей базы, не из входящего JSON.
- Crypto Pay: API Token, вебхук `/cryptobot-webhook`. Нужен стандартный `crypto-pay-api-signature` от провайдера.
- Heleket: Merchant ID + API Key + домен, вебхук `/heleket-webhook`. Подпись использует MD5 согласно протоколу Heleket; это не рекомендуемый алгоритм для собственных новых протоколов.
- TON: отключён, `/ton-webhook` отвечает `503`. Не предлагайте этот способ покупателям.

Перед запуском проверьте требования провайдера, фискализацию, возвраты и применимое законодательство. Этот репозиторий не подтверждает возможность принимать деньги без регистрации или чеков.

### Состояния платежей и восстановление

`pending → verified → processing → paid` либо `review`.

- `pending`: подтверждения нет; при неработающем обработчике вебхук получает `503` для повтора.
- `verified`: подтверждение сохранено в SQLite. Планировщик возобновляет выдачу после перезапуска (проверка раз в 5 минут, первая — через 10 секунд).
- `processing`: счёт атомарно захвачен обработчиком. После аварии требуется сверка — неизвестно, успел ли Hub применить продление.
- `paid`: ключ сохранён и обработка завершилась.
- `review`: подтверждение получено, но выдачу/учёт нужно проверить вручную. Не просите пользователя платить повторно.

**Не переводите `review`/`processing` обратно в `pending` вслепую**: это может повторно продлить существующий ключ. Проверьте счёт у провайдера, пользователя/срок на Hub и нодах, запись ключа и начисления рефералу. Затем вручную завершите выдачу либо возврат и учёт. Автоматической распределённой exactly-once транзакции между SQLite и RIXXX здесь нет.

## Результаты аудита и проверки

Аудит выполнен относительно исходного бота `c7e3039` и API панели `423ae6525359576c1f46bb38bf9030b707911cf4` (package version 1.11.4).

Исправлены: известный секрет сессий, вход `admin/admin`, plaintext-пароль веб-админки, отсутствие CSRF, неподтверждённые платёжные вебхуки, гонка обработки счетов, повторный триал через прямой callback, перехват админ-команд общим обработчиком, стирание неотозванных ключей, IP-cookie авторизация, потеря уведомлений планировщика, небезопасные настройки запуска. Обновлены уязвимые зависимости, удалены неиспользуемые старые интеграции.

```bash
python3 -m venv .venv
.venv/bin/pip install -e .
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python -m compileall -q src
bash -n install.sh
```

На Python 3.13: **97 тестов прошли**. Используются настоящие Flask, aiogram и SQLite; внешние Telegram/платёжные/RIXXX вызовы заменены контролируемыми ответами. Проверены и сборка wheel с HTML/static-ресурсами, и `pip check`, и отсутствие неопределённых имён средствами Ruff. `pip-audit` после обновления не обнаружил известных уязвимостей в проверенном окружении; это не гарантия отсутствия новых или неизвестных проблем.

Отдельно в неизменённом репозитории панели прошли 153 проверки функций подписок, бонусных URI, выбора формата клиента и XHTTP. Это **не сетевой end-to-end тест** и не проверка установленных приложений Karing/Shadowrocket.

Bandit продолжает отмечать MD5 протокола Heleket и литералы миграции/пустых настроек; находки не скрывались. Полный security-аудит самой RIXXX-панели, ОС, reverse proxy и внешних провайдеров не выполнялся. Docker runtime/build в данной песочнице не проверен: Docker отсутствует.

### Обязательная приёмка перед рабочими продажами

1. Сделать резервные копии, создать отдельного тестового покупателя.
2. Проверить вход, CSRF, 2FA, запуск/остановку бота и права саппорта.
3. Выдать ключ, проверить его на Hub и каждой ноде федерации.
4. Добавить бонусный VLESS URI и обновить ту же подписку в реальных Karing/Shadowrocket. Проверить поддерживаемые транспорты и маршрутизацию.
5. Совершить согласованный тестовый платёж, проверить сумму, ключ, один период продления и одно реферальное начисление; повторить вебхук и кнопку проверки.
6. Остановить бота при доставке вебхука, затем восстановить: проверить повторную доставку/`verified`-очередь.
7. Отключить одну ноду, выполнить отзыв и убедиться, что ошибка не считается успехом; восстановить ноду и повторить отзыв.
8. Проверить истечение срока, переподписку после удаления пользователя панелью, резервное восстановление БД и логи.

## Ограничения эксплуатации

- SQLite хранит сервисные токены и пароли хостов в открытом виде; защищайте диск, каталог и резервные копии. Файл БД получает права `0600`; пароль веб-админа хранится хешированным.
- Compose пока монтирует каталог проекта и не переводит контейнер на отдельного непривилегированного UID. Для дополнительной изоляции нужны отдельный data-volume и проверка миграции прав на вашем сервере.
- Лимит попыток входа — общий для процесса (10/минуту); rate limit и ограничения административных маршрутов на reverse proxy рекомендуются дополнительно.
- Удаление просроченного пользователя панелью может уничтожить его токен и бонусный список. При последующей покупке бот выдаст новый токен; восстановите нужные бонусы отдельно.
- `/give` использует первый хост. Для одной подписки по всем странам настройте одну запись Hub и федерацию в RIXXX, а не независимые хосты в магазине.
- Нет автоматической компенсации частичного deploy, полноценного менеджера возвратов и автоматической сверки всех состояний панели. Ошибки требуют внимания оператора.
