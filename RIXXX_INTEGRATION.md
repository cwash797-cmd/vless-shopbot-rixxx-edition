# Подключение магазина к RIXXX Hub

Актуальные ограничения, платежи, миграция и приёмка описаны в [README](README.md). Старый отчёт о полной совместимости с 3x-ui и входе `admin/admin` не является инструкцией для этой ветки.

## Два независимых направления трафика

1. Telegram-магазин → административный API RIXXX: создание/продление/отзыв пользователей.
2. Клиентское приложение → публичный `/sub/:token`: получение конфигурации без административного пароля.

Бот не проксирует VPN-трафик и не формирует конфиги sing-box сам. Источник единой подписки — Hub RIXXX. Настройте публичный subscription base URL в панели и сначала убедитесь, что пользователь, созданный вручную в RIXXX, может импортировать подписку.

## Доступ бота к API панели

Для внешнего доступа используйте HTTPS и правильный секретный префикс панели:

```text
https://<basic-auth-user>:<basic-auth-password>@panel.example.com/<webBasePath>/
```

Логин/пароль в URL предназначены для Basic Auth reverse proxy; отдельные поля «Логин панели»/«Пароль панели» — для `POST /api/login`. Они могут отличаться. Спецсимволы в URL credentials должны быть percent-encoded. Не копируйте этот административный URL в сообщения покупателю.

Если Caddy Basic Auth не включён, credentials в URL не нужны. Адрес локальной панели RIXXX обычно `http://127.0.0.1:3000`, **не `2053`**. В обычном Docker-контейнере `127.0.0.1` — сам контейнер, не VPS. Самый простой вариант — подключаться к внешнему HTTPS-домену панели. Не открывайте необработанный порт `3000` в интернет ради Docker.

Поле inbound ID в этой версии не используется: поддерживается API RIXXX, не API 3x-ui.

## Веб-панель магазина и reverse proxy

Compose публикует только `127.0.0.1:1488`. Нужен отдельный домен, например `bot.example.com`, и HTTPS reverse proxy.

Если существующий Caddy настроен на поддерживаемый отдельный include, фрагмент сайта выглядит так:

```caddyfile
bot.example.com {
    reverse_proxy 127.0.0.1:1488
}
```

Это **фрагмент**, а не команда для замены рабочего Caddyfile. Сначала выясните, какой файл реально загружает Caddy и не перегенерирует ли его RIXXX. Сделайте резервную копию и проверьте конфигурацию штатным валидатором Caddy перед reload. При отсутствии механизма устойчивого include выберите отдельный reverse proxy/сервер, не конкурирующий за занятые порты.

Не дописывайте `module.exports.render` в исходники панели и не запускайте `update.sh --repair` только ради магазина: это может затронуть действующие VPN-сервисы. Эта ветка не меняет Caddy/Nginx автоматически.

Платёжные POST-маршруты `/lava-webhook`, `/yookassa-webhook`, `/cryptobot-webhook`, `/heleket-webhook` должны быть доступны провайдерам по HTTPS без интерактивного логина reverse proxy. Они проверяют собственную аутентификацию/подтверждение. Административные страницы можно дополнительно ограничить по IP на reverse proxy, не закрывая webhook-маршруты.

## Федерация и одна подписка

В магазине добавьте одну запись Hub. В RIXXX настройте нужные федеративные ноды и проверьте их токены/доступность.

Последовательность выдачи:

1. `POST /api/login`, сессионная cookie сохраняется, в том числе для явно настроенного IP-адреса.
2. `GET /api/users` и поиск по email/username.
3. `POST /api/users` или `PUT /api/users/:id`; срок рассчитывается в UTC, действующий период не теряется.
4. `POST /api/users/:id/federation/deploy`.
5. `GET /api/users/:id/sub-link` → передача готовой `/sub/:token` покупателю.

HTTP 200 у deploy не гарантирует успех каждой ноды. Бот проверяет `results[].ok`; при частичном результате локальная подписка сохраняется, администратору отправляется уведомление для проверки/повторного deploy в RIXXX. Ошибка 400 допустима как одиночный сервер **только** при точном ответе `No enabled federation nodes are configured.`

При отзыве вызывается undeploy с email, проверяются все результаты, затем удаление Hub-пользователя подтверждается повторным чтением. Если пользователь уже удалён на Hub, используется поддерживаемый RIXXX email fallback для отзыва на нодах. Неудача не приводит к потере локальной записи ключа.

## Бонусные ссылки

В личном чате владельца:

```text
/keys 123456789
/bonus 17 vless://... trojan://...
/bonus 17 clear
```

`17` — внутренний ID ключа магазина, не Telegram ID. Вторая команда заменяет весь персональный список через `PUT /api/users/:id/bonus-links`. Она не создаёт ключи в 3x-ui. Обновите подписку в клиенте после изменения.

На стороне RIXXX:

- Shadowrocket обычно получает base64-список URI.
- Karing/sing-box-клиенты получают JSON с теми бонусными протоколами/транспортами, которые умеет преобразовывать установленная версия панели.
- Поддержка URI в одном формате не гарантирует поддержку другим клиентом. Проверьте импорт и соединение на реальном устройстве.
- При обычном продлении существующего пользователя токен и бонусный список не меняются. Если панель уже удалила просроченного пользователя, создаётся новая запись и новый токен; бонусы нужно восстановить отдельно.
- Отзыв RIXXX-подписки не аннулирует скопированный VLESS/другой ключ стороннего сервера. Его отзыв выполняется отдельно у источника.

## Диагностика

| Симптом | Проверить |
|---|---|
| 401 при входе в RIXXX | Basic Auth, логин панели, секретный префикс; не публиковать credentials в логах |
| Нет ссылки после выдачи | Public subscription URL, сохранение пользователя, авторизация API |
| В подписке только Hub | `results[].ok`, email пользователя на нодах, доступность федерации |
| Нет бонусного VLESS в JSON | Версию панели, парсер транспорта, совместимость приложения |
| Вебхук 403 | Подпись/ключ, провайдера, сумму и валюту локального счёта |
| Вебхук 503 | Настройки/состояние бота, цикл событий, сохранение счёта, доступность API провайдера |
| `review`/зависший `processing` | Ручную сверку оплаты и удалённой выдачи до любых повторных действий |
| Веб-панель не держит вход | HTTPS при `COOKIE_SECURE=true`, постоянный `FLASK_SECRET_KEY` |

Ответ 405 на GET к вебхуку проверяет только наличие POST-маршрута. Он не доказывает правильность ключей, платежей, выдачи или доступности VPN.
